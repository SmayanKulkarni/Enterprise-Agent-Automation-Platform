# Tenant OpenRouter connection and Studio clarity

Status: planning design. No implementation is authorized by this document.

## Outcome and scope

A tenant administrator can configure, verify, rotate, and disconnect that tenant's OpenRouter API key in the authenticated deployed UI. An editor can select an approved exact OpenRouter model for an Agent and see why it is unavailable. A checked and published workflow pins the model and existing policy; a run uses only its own tenant's server-held key. Studio makes Manual and signed Webhook Trigger modes understandable, keeps the live palette executable, and repairs the crowded library and selected-node layout at verified viewport widths.

This design assumes tenant-funded BYOK only and tenant administrator authority for connection changes. Azure OpenAI remains the default. It does not introduce a platform-funded OpenRouter fallback. The fixture-only outbound Webhook block stays outside the live palette. An outbound HTTP/Webhook effect would need a separate design for destination control, SSRF prevention, credentials, idempotency, receipts, approval, and unknown outcomes. These assumptions resolve ambiguous handoff language without silently extending workflow execution.

The existing Studio guidance tickets remain authoritative for work already done. In particular, `.scratch/studio-ux-guidance/issues/01`, `03`, `04`, `06`, and `07` are complete or done; `02` is in progress, and `05` is ready. New tickets should reference those seams and avoid duplicating them.

## Options considered

1. **Tenant BYOK in the existing workflow service (chosen).** Add one encrypted tenant connection record and one narrow secret submission path. Reuse the workflow store, publication check, HTTP model adapter, and existing Studio. This keeps authorization and tenant scoping in the same service that publishes and runs workflows.
2. **Global platform OpenRouter key with a tenant allow-list.** This is close to current code but cannot deliver tenant credential management, tenant-paid billing, or isolated rotation. Retaining it as an implicit fallback would allow a disconnected tenant to consume platform credentials.
3. **New integration service.** A separate vault service could own credentials and catalogs but adds deployment, network, and failure boundaries without a V1 need. Reconsider only if several providers require shared credential operations.

## Current path and architecture

The live UI is `StudioEditor` in `apps/browser/src/platform-app.tsx`. `workflow-model.ts` provides the Azure OpenAI starter Agent. `PlatformApi` submits generic commands to `BrowserV1Transport`, which authenticates a Clerk session, checks tenant context, validates command envelopes, and dispatches to `workflowCommandHandlers`. `WorkflowService.check` and `publish` call the graph validator and provider readiness check. Azure SQL stores drafts and published definitions. Azure Durable Functions invokes `WorkflowWorker.agentStep`, which calls `HttpModelPort.complete`. Today the adapter reads `OPENROUTER_API_KEY` and `WORKFLOW_OPENROUTER_TENANTS` from process environment, while the browser host treats the presence of the global key as provider readiness.

Add a single tenant connection record with a stable per-tenant ID, status, version, last verified time, and encrypted secret envelope. The record lives in the existing tenant-scoped workflow store; the SQL kind constraint must be extended. The envelope contains a key version, random nonce, ciphertext, and authentication tag. Encrypt with Node's authenticated AES-256-GCM, bind the tenant ID and provider name as associated data, and load versioned wrapping keys only from server configuration. In Azure Functions, a Key Vault reference can supply that configuration through managed identity; startup must fail for malformed or absent keys when the connection capability is enabled. Keep old wrapping keys until records are re-encrypted. The repo has no existing encrypt/decrypt path to reuse; the current webhook credential record stores a generated signing secret in SQL JSON and is not a safe precedent for tenant-supplied API keys. [Azure documents Key Vault references for Functions](https://learn.microsoft.com/en-us/azure/app-service/app-service-key-vault-references?tabs=azure-cli).

Use a dedicated authenticated secret submission route under the existing browser API transport. It accepts an administrator's key once over TLS, with a small body limit, Origin check, tenant authentication, current membership/profile check, expected version, and idempotency key. It bypasses generic browser command arguments and contracts because `decodeCommandArguments` rejects credential keys and the generic command path digests the full argument object. The route validates the key, encrypts immediately, writes only ciphertext and safe metadata, and returns status/version; raw key bytes never enter command receipts, contract envelopes, logs, projections, draft JSON, run history, or browser storage. Rotation uses the same route and version check. Disconnect is an admin-only state change that removes the active ciphertext from the current record. The UI clears the input after submission and never echoes it. Failed key verification does not replace a working key; an explicit test operation reports a redacted outcome and updates last-verified metadata when successful. OpenRouter documents a [current-key endpoint](https://openrouter.ai/docs/api/api-reference/api-keys/get-current-key) suitable for non-generation verification. Verification results must be mapped to safe categories without relaying upstream bodies.

Expose only a redacted tenant connection projection: status (`not-configured`, `ready`, `invalid-credential`, `disabled`, or `unavailable`), record version, last verified time, and permitted model metadata. Model policy is a server-owned exact allow-list with a conservative maximum cost rate per model. This is the smallest enforceable policy; no tenant model policy editor is planned. A tenant's key does not grant permission to arbitrary model IDs. The allow-list is checked on Agent edit feedback, server check, publication, and execution. At publication, require the connection to be ready, `openRouterOptIn: true`, an exact allowed model and allowed same-provider fallback if present, a supported strict JSON-schema response, and the existing Node policy. Pin the exact strings in the published definition. OpenRouter states that [structured output support varies by model](https://openrouter.ai/docs/guides/features/structured-outputs); model certification must use the catalog's supported parameters and a live test before adding a model to the allow-list. Aliases and moving targets are not allowed in the list. The existing `WORKFLOW_MAX_COST_PER_1K_TOKENS` calculation is shared; the OpenRouter path must use the configured conservative rate for the selected model so the Node policy cost check cannot understate a pricier model.

`WorkflowWorker.agentStep` already builds a `ModelRequest` with tenant ID, provider, model, schema, and policy. Keep that request free of credential material. Change `HttpModelPort` construction in `azure-functions/src/functions/workflow-run.ts` to receive a server-only tenant credential resolver. For OpenRouter, it resolves and decrypts the tenant's current connection just before dispatch and denies missing/disabled/invalid states. Azure OpenAI keeps its current server configuration. Remove the old implicit global OpenRouter key and tenant allow-list only after this path is live; an existing published OpenRouter definition without a tenant connection then fails closed. `WorkflowService.check` and `publish` read the same connection readiness as the worker. `publish` must recheck after check evidence, and execution must recheck after publication so disconnect or rotation takes effect for subsequent attempts. Rotation may affect an in-flight request already dispatched; no automatic replay is implied.

## Studio behavior

Put Provider Connections near the live Studio workspace, visible as status to editors and actionable only to tenant administrators. Give the key input a clear one-time submission flow, redacted readiness, Verify, Rotate, and Disconnect actions. Provide an explicit error state when Azure SQL or key configuration is unavailable. Tenant switching clears transient input and connection projection. The Agent inspector gets typed provider, exact model, optional allowed fallback, response schema, opt-in, and Node policy controls. Reuse existing graph fields and validator. The key is never requested in the Agent inspector. A disabled or missing connection explains the next action; a publish attempt remains server authoritative.

For Trigger, finish the existing `02-live-studio-guidance` ticket: explain Manual versus signed Webhook ingress beside the mode selector; separate field schema from a sample run; link a published webhook Trigger to `WebhookPanel` for URL, provisioning, and signed testing. Name the fixture-only “Send webhook” item as an outgoing action that is not currently executable in live Studio. Do not add it to `liveLibrary`. The existing `WebhookPanel`, `workflow.test-webhook` command, and `deliverWebhook` path remain inbound only.

For the reported crowded Studio, reproduce the current three-step graph at desktop, tablet, and mobile widths, including the user's viewport if supplied later. The source points to fixed grid tracks (`224px minmax(500px,1fr) 330px`, then `190px minmax(430px,1fr) 280px`) and 9–11px library/inspector text, but a screenshot alone does not establish the exact breakpoint failure. Adjust the existing grid, card wrapping, font sizes, and narrow-screen library access after reproduction; preserve canvas zoom/drag behavior and keyboard access. Do not create a new editor shell.

## Blast radius and failure behavior

| Boundary | Supported impact and check |
| --- | --- |
| Browser transport and API | New secret path must not weaken `decodeCommandArguments`, generic projection redaction, session/tenant checks, origin enforcement, body limits, or error normalization. Verify key strings never appear in responses, logs, browser state persistence, generic command maps, or contract envelopes. |
| Azure SQL workflow records | Add one record kind and compatible migration without editing the user's pending `007_webhook_admission_and_history.sql` change. Verify tenant partition, expected-version races, replay behavior, and that old records and projections remain readable. |
| Graph and publication | Azure OpenAI drafts and published definitions must remain valid. OpenRouter drafts need connection/model/schema diagnostics; publication pins exact model/fallback and rejects stale or disconnected connections. |
| Worker and retries | Resolve by trusted run tenant, not client-supplied tenant or environment allow-list. Disconnect fails future dispatch closed. Retry/circuit behavior and Azure summary generation remain intact. A failed OpenRouter call never falls back to an unapproved model or the platform key. |
| Studio and responsive layout | Retain existing save, draft selection, Trigger input, webhook test, zoom, inspector keyboard use, and fixture/live distinction. Check at 1440, 1024, 768, and 390 CSS pixels and at 200% browser zoom; record the actual problematic viewport during implementation. |
| Operational rollout | Provision wrapping key and model allow-list before enabling UI. Deploy SQL migration, then server secret path/resolver, then authoring controls. Keep OpenRouter publication disabled until deployment config and a real tenant smoke test pass. Rollback hides the new controls and denies new OpenRouter dispatch; ciphertext records remain recoverable with retained key versions. |

## Verification and acceptance

- An admin can save, verify, rotate, and disconnect a key; another tenant and a non-admin cannot read or mutate it. No later projection or response reveals the key.
- An editor selects an allowed exact model; check and publish reject absent connection, unapproved model, unsupported schema capability, missing opt-in, and stale revision. A published run uses only the correct tenant's credential.
- Azure OpenAI starter, summary, existing webhook ingress, manual Trigger, and durable retry/circuit paths continue to work.
- Trigger mode and signed webhook setup are understandable in the selected-node flow. The outgoing fixture block is not portrayed as a live action.
- At reproduced viewport sizes, building blocks and selected-node fields remain readable, reachable, and keyboard operable without hiding live authoring actions.
- Focused tests cover authenticated admin key lifecycle, ciphertext isolation, tenant separation, model-policy enforcement at publication and runtime, safe errors, and neighboring Azure/webhook behavior. A real deployed tenant smoke test uses a deliberately limited test key and checks only redacted results.
