# Agentic Operational Memory integration for Diagram Workflow V1

**Status:** ready-for-agent
**Triage:** ready-for-agent
**Extends:** Diagram Workflow V1 Model and Operational Memory

## Problem Statement

A user can place a Memory node in Solution Studio and an administrator can import one validated Run Summary by run ID, but a Workflow Run cannot yet use durable, concurrent, governed Operational Memory. The current worker lists SQL summaries, embeds every candidate during retrieval, and exposes no Agent proposal, lifecycle, or provider-readiness path. The browser shows a run-pinned import form but cannot create the agreed live source-definition import, revoke it, or inspect redacted memory state and retrieval history. A completed workflow therefore cannot reliably carry validated facts or explicitly stated preferences into later authorized runs.

## Solution

Extend the published Workflow Definition and authenticated Studio journey so an Agent can propose bounded, source-linked task facts or explicitly stated user preferences, and the server can validate and automatically promote them alongside Run Summaries. Store Operational Memory content and vectors in tenant-partitioned Upstash Vector, with Azure SQL holding immutable Run History and non-content lifecycle and audit evidence. Let an explicit Memory node retrieve bounded, eligible evidence from its own Workflow Definition or an active administrator-published Memory Import. Give operators redacted status and provenance, and give tenant administrators live import and lifecycle controls through the existing browser API. Empty, disabled, and unavailable memory leave the Workflow Run outcome intact.

## User Stories

1. As a tenant editor, I want to place a Memory node in a Workflow Definition, so that a later Agent can use authorized prior evidence.
2. As a tenant editor, I want to set a Memory node's item and character limits, so that retrieval stays within the published budget.
3. As a tenant editor, I want a published revision to pin Memory node policy, so that a running workflow uses the reviewed bounds.
4. As a workflow operator, I want a completed run to produce a source-linked Run Summary asynchronously, so that its outcome may help later runs without delaying completion.
5. As a workflow operator, I want summary failure to appear in run status, so that I can distinguish missing context from successful promotion.
6. As an Agent, I want to propose a task fact with an exact validated source, so that later runs can use evidence observed during this workflow.
7. As an Agent, I want to propose a preference explicitly stated by an identified user, so that later runs can respect that user's stated preference when authorized.
8. As a user, I want unsupported claims, inferred traits, secrets, and proposed instructions excluded, so that Operational Memory cannot invent identity or authority.
9. As a tenant administrator, I want the server to derive tenant, Workflow Definition, owner, and item identity, so that an Agent cannot select a broader scope.
10. As a workflow operator, I want invalid proposals to remain non-retrievable with a visible failure state, so that a completed run is not silently changed.
11. As a workflow operator, I want identical promotions to resolve to one item after retry or replay, so that durable activity delivery does not create duplicates.
12. As a workflow operator, I want a valid item to become retrievable automatically, so that no manual promotion queue blocks the next run.
13. As a workflow operator, I want transient embedding and vector failures retried with a bounded limit, so that recoverable outages do not lose eligible memory.
14. As a workflow operator, I want exhausted failures to remain visible but non-retrievable, so that a provider outage never contaminates future prompts.
15. As a tenant member, I want memory isolated by tenant and stable Workflow Definition ID across its revisions, so that another workflow cannot recall it implicitly.
16. As an identified user, I want owner-scoped items returned only when the retrieving run has the same validated owner, so that my preferences do not appear for another person.
17. As a tenant administrator, I want to publish a Memory Import from a source Workflow Definition to a specific target revision, so that another workflow can use that source's eligible summaries and items.
18. As a tenant administrator, I want an import to include newly promoted source items while active, so that I do not need to attach each run separately.
19. As a tenant administrator, I want to revoke a Memory Import, so that future retrieval stops without rewriting earlier Run History.
20. As a workflow operator, I want import grants, revocations, and retrievals recorded with provenance, so that I can explain why an item was available.
21. As a workflow operator, I want Memory retrieval to use the validated run input and a tenant-scoped vector query, so that an Agent cannot choose an arbitrary recall query.
22. As a workflow operator, I want eligibility checked after vector search, so that stale provider metadata cannot bypass current scope or lifecycle state.
23. As an Agent, I want retrieved material clearly marked as untrusted, source-linked evidence, so that it cannot override the published instructions or Capability grants.
24. As a workflow operator, I want the Memory node to return only bounded, redacted items with source metadata, so that prompt context remains auditable and safe.
25. As a workflow operator, I want an empty result represented explicitly, so that a later Agent can proceed without invented context.
26. As a workflow operator, I want provider unavailability represented explicitly while the run continues, so that memory outages do not change the workflow result.
27. As a tenant administrator, I want to correct an item by creating a successor and withdrawing its predecessor, so that future recall uses the correction while old evidence remains intact.
28. As a tenant administrator, I want to withdraw an item or invalidate its source, so that it immediately stops appearing in later retrievals.
29. As a tenant administrator, I want expiry, legal hold, and deletion controls, so that Operational Memory follows its governed lifetime.
30. As a tenant administrator, I want physical vector deletion after an eligible deletion request, so that withdrawn content is removed from the hosted store.
31. As a workflow operator, I want to inspect redacted item status, source reference, producing revision, expiry, and failure metadata, so that I can investigate memory behavior without viewing content.
32. As a workflow operator, I want to inspect retrieval provenance on a Workflow Run, so that I can explain which source items informed an Agent.
33. As a tenant administrator, I want import and lifecycle controls to show current state and command feedback, so that I can tell whether my change was applied or denied.
34. As a tenant member, I want memory controls to disappear or become read-only when I lack authority, so that the interface reflects my role while the server enforces it.
35. As a tenant member, I want provider readiness to show disabled, not configured, ready, or unavailable state, so that a missing integration is not mistaken for an empty memory store.
36. As a tenant member, I want tenant switching and sign-out to clear memory projections, so that another tenant's metadata never remains on screen.
37. As a tenant administrator, I want the feature disabled for tenants until its live gates pass, so that existing Workflow Runs retain their current behavior during rollout.
38. As a tenant administrator, I want rollback to stop new promotion and retrieval while preserving audit evidence and queued deletion work, so that an incident can be contained safely.

## Implementation Decisions

- Reuse the existing Solution Studio graph, compiler, published Memory node configuration, sequential durable Workflow Run, Run History, authenticated browser transport, Clerk membership checks, and tenant-scoped workflow store. The extension does not introduce another editor or browser API.
- Preserve the existing Run Summary activity as the source-validation entry point. Promote validated summaries and Agent-authored items through the same server-governed workflow memory path. Move retrievable summary text out of the current SQL summary record shape; SQL keeps source references, state, digests, and lifecycle receipts but no recoverable Operational Memory content or embeddings.
- Accept only bounded proposals for a task fact or an explicitly stated user preference. A proposal contains candidate text, exact source ID and digest, supporting excerpt, and a subject for a preference. The server verifies the immutable same-tenant, same-definition source and excerpt after redaction, derives scope and identity, and rejects an excerpt or candidate changed by secret redaction.
- Give each accepted item an immutable identity, producing revision, source link, optional owner, and deterministic fingerprint. A duplicate fingerprint succeeds without creating another item. A correction creates a successor within the same scope; lifecycle resolution excludes the predecessor from future retrieval.
- Keep provider credentials in worker activities. Add a narrow hosted-memory port with idempotent upsert, bounded query, and remove operations, backed initially by Upstash Vector REST. Use one namespace per tenant, server-derived metadata, a pinned embedding model and dimension, and deterministic item IDs. No browser credential or provider SDK is needed.
- Replace candidate-wide summary scanning and embedding with one bounded query embedding and one provider `topK` request per Memory node. Enforce tenant, stable definition or active import, optional owner, promoted state, expiry, withdrawal, source validity, and legal-access restrictions both before provider access and again on returned results. Provider filtering is an optimization, not authorization.
- Keep embedding, promotion, retrieval, deletion, and retries in durable activities outside orchestration replay. Retry transient promotion failures up to three times. Invalid proposals and exhausted failures remain non-retrievable; neither changes the completed Workflow Run.
- Keep the Memory node's published `limit` and `maxChars` as the V1 retrieval and prompt budget. Return a bounded `memory` result with `items` and a distinct empty or unavailable status. Include only redacted text, item type, stable item and source IDs, source digest, producing definition and revision, and score. Apply the total character cap including provenance labels. Pass this result to later Agent prompt assembly as delimited, untrusted evidence; Agent nodes never retrieve implicitly.
- Replace the existing run-ID and summary-digest import contract with an administrator-published, target-revision-pinned attachment to a source Workflow Definition. Resolve active imports at retrieval time, preserve source-owner filters, reject cross-tenant grants, and audit grant, revoke, and retrieval. Revocation affects future retrieval only.
- Reuse the existing memory lifecycle vocabulary where it fits, exposed through workflow-specific, tenant-scoped commands and projections. Administrators can correct, withdraw, hold, release, shorten expiry, and request deletion; operators can read redacted metadata only. Withdrawal, expiry, source invalidation, and deletion immediately fail the server eligibility recheck and enqueue an idempotent vector update or removal. A legal hold prevents physical deletion but never restores retrievability.
- Extend the existing browser command allowlist, argument validation, workflow service, and projection collection registry for source-definition imports, revocation, lifecycle commands, memory status, and retrieval provenance. The server checks role, tenant, target revision, expected version, and idempotency; browser visibility is only a presentation aid.
- Rework the existing Memory Import panel to select a source Workflow Definition, show the pinned target revision and active or revoked state, and let an administrator revoke an attachment. The current source-run UUID form and summary-import wording must be replaced.
- Design and implement a new Studio Memory view for redacted items, source and owner scope, promotion or failure state, expiry, holds, predecessor or successor, and retrieval history. Provide administrator actions there with clear confirmation and result feedback. Integrate the view with the existing published-definition and Run History surfaces, including empty, loading, error, disabled, and provider-unavailable states. The existing generic fixture Memory route is not a live workflow memory console.
- Add a server-derived provider-readiness projection to the Studio view. The existing Vercel project must be linked before the chosen Upstash integration can provision real credentials. Until then the UI reports readiness accurately and does not simulate hosted retrieval.
- Start disabled for every tenant, with no historical backfill. The first rollout tenant requires static, workflow, browser, and live provider certification. A model, dimension, or provider change uses a new empty namespace and new certification rather than an in-place vector rewrite.

### Contracts and functions to define

- `resolveMemoryScope(publishedDefinition, run)` returns a server-derived tenant ID, stable Workflow Definition ID (`draftId`), published definition ID, and producing revision. `WorkflowRun.definitionId` currently identifies a single published revision; it must not be used alone as the cross-revision scope key. For new runs, persist the stable ID on the run or resolve it from its pinned published definition before any memory operation.
- `validateMemoryProposal(proposal, source, run)` accepts only `task-fact` and `stated-preference`, verifies a bounded candidate, exact source ID and digest, supporting excerpt, and identified preference subject, and returns redacted, normalized data or a terminal rejection. Use a deterministic source reference derived from run ID plus validated input or ordered Run History event; do not treat a model-supplied user ID as proof of who stated a preference.
- `memoryFingerprint(validatedProposal, scope)` uses the existing canonical JSON and SHA-256 utilities over stable scope, type, source ID and digest, optional subject, and normalized redacted text. `memoryItemId(fingerprint)` derives the same UUID on every retry. Compare a pre-existing item's fingerprint before treating an insert conflict as a successful duplicate.
- `stageMemoryProposal(runId, proposal)` validates against the bounded Agent result and its exact source reference, embeds redacted text once, and writes it to the tenant's hosted store as non-retrievable pending data with a content-free SQL reference. A stage failure records a non-retrievable failure without failing the Agent node. `promoteMemoryItem(runId, stagedItemId)` checks the completed run and persisted source, fetches the pending item through the server-only port, and changes it to promoted with an idempotent upsert and content-free outcome receipt. Repeated delivery must converge on one item and one effective outcome.
- `promoteRunSummary(runId)` reuses the existing summary generation and source check, then uses the same hosted promotion path. The SQL summary record becomes a content-free source and status reference; the hosted record holds retrievable redacted text. Do not backfill old SQL summaries implicitly.
- `memoryEnabled(tenantId)` reads a server-side tenant allowlist that defaults to disabled. Both promotion and query activities check it; readiness distinguishes disabled from missing provider credentials. Use the existing Azure embedding configuration and server-only `UPSTASH_VECTOR_REST_URL` and `UPSTASH_VECTOR_REST_TOKEN`; pin the exact embedding model and dimension before enabling a tenant.
- `HostedMemoryPort.upsert(item, vector)`, `.read(tenantNamespace, itemId)`, `.query(tenantNamespace, queryVector, filter, topK)`, and `.remove(tenantNamespace, itemId)` form the narrow provider boundary. `read` is used only for pending promotion and lifecycle work. Implement one `UpstashVectorMemoryPort` using the installed Node runtime's HTTP primitives. Decode provider responses as untrusted data; reject malformed IDs, vectors, scores, and metadata before returning them to the workflow service.
- `queryOperationalMemory(run, memoryNode)` derives allowed definition and owner scopes from the run and active imports, embeds the canonical validated input once, requests at most the node limit, rechecks every returned ID against current SQL lifecycle and import state, orders eligible results by score, promotion time, and ID, and applies one total `maxChars` budget including source labels. Return explicit `success`, `empty`, or `unavailable` status with `items` under the Memory node output.
- `applyMemoryLifecycle(context, command)` checks tenant-admin authority, expected version, request ID, target scope, and legal hold, then appends an immutable lifecycle receipt and queues any provider removal. Correction calls the same proposal-validation and promotion path for a successor before withdrawing its predecessor. Effective eligibility must change immediately, even while vector deletion is pending.
- `discardPendingMemory(runId)` removes staged records after a terminal failed run. A lifecycle cleanup activity removes any remaining expired pending records, including those left by interrupted activity delivery; pending records are never eligible even if cleanup is delayed.
- `publishMemoryImport(context, targetPublishedId, sourceStableDefinitionId, requestId)` verifies both definitions belong to the tenant, pins the target published revision, and writes an active attachment. `revokeMemoryImport(context, importId, expectedVersion, reason, requestId)` records prospective revocation. Runtime retrieval evaluates the active attachment for the run's pinned target revision, not merely the target's display name.
- `projectWorkflowMemory(context, definitionId)` returns only status, IDs, source kind and digest, producing revision, owner scope indicator, predecessor/successor links, timestamps, expiry, hold and failure status, plus action versions. `projectMemoryReadiness(context)` returns server-derived tenant flag and provider state. Extend the existing Workflow Run projection with retrieval IDs, import ID when applicable, result count, status, and failure category; never include prompt text in these browser projections.

### Agent output and activity sequence

1. Extend the published Agent response schema with an optional, fixed `memoryProposals` array when that Agent is allowed to propose memory. Bound the array to three entries and each candidate to 1,000 characters as V1 validation limits; these are implementation caps, not extra authoring controls. Each entry carries type, text, source ID, source digest, supporting excerpt, and optional subject. The existing general `JsonSchema` validator is shallow, so add validation for this one known nested shape at the Agent trust boundary instead of introducing a general schema engine.
2. Let `agentStep` validate the complete structured output, stage proposals as non-retrievable, then write the completed Agent event with the ordinary result and pending IDs or failure statuses only. A stage failure does not fail the node; replayed staging converges on deterministic IDs. Strip proposal text from SQL run output and browser projections. Never pass proposed text into a Memory node as already trusted memory.
3. After the End node completes, invoke summary generation and pending Agent proposal promotion as separate durable activities. One failure cannot suppress the other, and neither can change `WorkflowRun.status = completed`. Replayed activities use deterministic IDs and persisted receipts. On a terminal failed run, invoke pending-item cleanup; an expiry cleanup activity handles interrupted delivery.
4. On a later run, `memoryStep` obtains only hosted candidates, performs the SQL-backed eligibility recheck, and writes a bounded `memory` output and redacted retrieval receipt. `agentStep` consumes that output only when it is on the executed path before the Agent node.
5. Lifecycle changes update the authoritative eligibility ledger before asynchronous vector removal. A stale hosted match is dropped by the recheck. No cache may bypass that check.

### Browser API and frontend wiring

- Keep `PlatformApi.command` and `.projection` as the sole frontend transport. Change `workflow.import-memory` arguments from `{ id, sourceRunId }` to `{ id, sourceDefinitionId }`, where `id` is the target published definition ID. Add `workflow.revoke-memory-import` with import ID and reason, and workflow-scoped `correct-memory`, `withdraw-memory`, `hold-memory`, `release-memory-hold`, `set-memory-expiry`, and `delete-memory` commands. Extend `COMMANDS`, `argumentKeys`, the handler table, and server service together; reject unknown fields at both boundaries.
- Keep `workflow-memory-imports` and `workflow-runs` projections. Add `workflow-memory-items` and `workflow-memory-readiness` collections to the browser registry and route them through `WorkflowService.projection`. The existing generic `memory` fixture collection remains unrelated to the live workflow view.
- Change `MemoryImportPanel` to load published source definitions, submit a source definition ID, show active or revoked attachments and target revision, and issue revoke with the current record version. Refresh the projection after success or conflict.
- Add a `WorkflowMemoryPanel` to the authenticated Studio beside the current import panel and run history. Show redacted item and retrieval metadata, failure and readiness states, and administrator lifecycle actions. Use the existing React state and CSS patterns, native form controls, and accessible labels/status messages. Clear state on tenant change or sign-out as the Studio already remounts by tenant ID.
- A browser user may see only a restricted, redacted projection; item text and source excerpts are never serialized into browser responses. Button visibility follows the current profile, while the command handler still checks the authoritative server profile.

### Coding standards and libraries

- Use the repository's TypeScript ESM style, `strict` and `exactOptionalPropertyTypes`, explicit `unknown` decoding at HTTP/model/browser boundaries, and the existing `digest`/`canonicalJson` helpers. Keep IDs and idempotency keys deterministic where activities may replay. Keep durable orchestration deterministic and side effects in activities.
- Use existing `durable-functions`, `@azure/functions`, `mssql`, React, Clerk, Vitest, and the built-in `fetch`, `crypto`, and `AbortSignal.timeout`. No new vector SDK, schema package, state library, or component library is required for this scope.
- Do not add code comments, as required by the repository instructions. Prefer small functions at the existing workflow service and port boundaries over new managers, registries, or one-use abstractions. Keep credentials, embeddings, and source text out of logs, SQL memory ledger records, and browser DTOs.
- Add the SQL change as the next numbered migration with a matching verification script. Keep tenant keys and owner procedures on all memory reads and writes. Enforce deterministic duplicate identity and expected-version conflicts in storage, not only in UI state.
- Use `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build:showcase`, and `pnpm build:azure` for relevant static and build gates, followed by SQL migration verification and the separate live Upstash certification when credentials exist. The key behavioral tests extend existing workflow end-to-end and browser contract tests rather than mirroring each helper.

## Testing Decisions

- Prefer one highest-level behavioral seam: an authenticated browser request through workflow commands and tenant-scoped persistence into a published Workflow Run, then a redacted Studio projection. Inject model and hosted-memory boundaries at that seam. Assert user-visible states, results, receipts, and authority decisions rather than private helper calls.
- Extend the existing workflow end-to-end and browser transport tests for proposal admission, duplicate promotion under replay, summary and item retrieval, owner and tenant isolation, active versus revoked imports, correction, withdrawal, source invalidation, expiry, hold, deletion, and empty or unavailable results. Verify that Agent nodes do not retrieve on their own and that provider failure never changes a completed run.
- At the same seam, test administrator and operator roles, stale revisions, idempotent commands, redacted projections, tenant switching, and the UI's active, revoked, loading, error, disabled, and unavailable states. Browser responses must contain no embedding, raw memory text, provider token, or secret.
- Use a narrow real-service certification check from the Azure runtime for Upstash namespace isolation, bounded `topK`, idempotent upsert and delete, concurrent Memory nodes, p95 latency, and forecast daily usage below 80% of the free-tier operation limit. This is the one necessary additional seam because a fake port cannot prove provider behavior.
- Prior art is the existing workflow end-to-end test, browser contract and transport tests, Studio command/store tests, and SQL verification scripts. Keep lower-level checks only where the high seam cannot reliably expose redaction, fingerprint, or retry edge cases.

## Out of Scope

- Cross-tenant sharing, implicit Agent recall, inferred personal traits, new instructions or Capability authority from memory, model training, and autonomous graph changes.
- Rebuilding Solution Studio, the graph compiler, durable traversal, Run History, or browser transport.
- SQL vector search, candidate-wide embedding scans, a second production vector provider, historical backfill, and in-place vector migration.
- Production-wide enablement before live provider and quota certification.
